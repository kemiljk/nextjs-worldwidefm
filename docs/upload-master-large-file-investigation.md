# Upload Master: large-file failures

Investigation: 4 October 2026. Production code: `aff298b`.

## Evidence

Sam's screenshot shows a 557.2 MB MP3, both destinations failing, and a Next.js
500 HTML document printed inside the Mixcloud error. The deployment identifier
in the screenshot matches the current production deployment.

The HTML display is confirmed: `parseJsonResponse` returned unparsed response
text as the public error. Regression tests reproduced this before the fix.
The local fix rejects malformed successful responses too, so an HTML response
cannot count as confirmation that the archive was updated. Error messages are
bounded, readable, and tell staff to check the destination before retrying.

Both provider helpers still buffer the whole source file. A local Node 25.9.0
probe streamed 584,266,548 bytes (557.2 MiB) from a mock source to the existing
helpers, with local mock destinations consuming the multipart request:

| Existing path | Peak process RSS |
| --- | ---: |
| Mixcloud | 1,244 MiB |
| RadioCult | 2,900 MiB |

These are local process measurements including the mock HTTP servers, not
production memory telemetry. The payload was generated bytes, not Sam's real
show. The probe demonstrates memory amplification; it does not establish the
cause of the specific production crash or validate provider audio processing.

A separate prototype using Node's HTTP request stream with backpressure sent
the same payload to a throttled local destination at a peak RSS of 165 MiB.
This supports streaming as the next direction. The prototype is not integrated
and does not yet implement ID3 replacement, provider retries, or durable jobs.

The production build log explicitly says the `memory` settings in `vercel.json`
are ignored on Active CPU billing. Vercel documents that function memory must
be configured in the dashboard. No dashboard memory setting was changed.
Read-only validation probes confirmed both production routes currently load
and return JSON when required fields are missing. The original crash logs have
not been recovered, so production memory exhaustion remains a hypothesis.

RadioCult documents MP3/M4A uploads **under 750 MB**; Mixcloud documents a
4 GB limit. Sam's file is below both documented size limits. The form currently
advertises a configurable 2 GiB allowance and formats beyond RadioCult's
documented support. Increasing timeouts or the form limit will not address that
mismatch or whole-file memory use.

## Implemented fix and verification

The current fix keeps the existing Vercel routes. It does not require another
hosting service.

- Both provider helpers now stream the source through Node multipart requests,
  with backpressure and redirect replay disabled. No full-audio Buffer or Blob
  is constructed. Requests explicitly bypass Next fetch caching.
- RadioCult metadata is rewritten using a bounded prefix read and a streaming
  skip of the previous ID3 tag. Audio checksums and multipart lengths match.
- Source and destination operations share deadlines and cancellation. A known
  RadioCult 5xx retry or Mixcloud validation fallback reopens the source. An
  ambiguous network failure or stalled accepted response does not replay a POST.
- A separate Next route initialization crash was reproduced locally: bundling
  Blob's OIDC/CLI dependencies leaves `xdg-app-paths` reading an undefined
  `require.main.filename`. Adding `@vercel/blob` to `serverExternalPackages`
  removes this failure without changing the browser Blob upload. Before the fix,
  actual local routes returned HTML 500 pages; afterward both returned JSON 200
  for 557.2 MiB transfers to local mock providers. Both Webpack development
  routes and the built Turbopack production routes passed.
- Browser response handling replaces HTML failures with bounded messages and
  refuses to count malformed responses as archive-save confirmation.

upload routes as well as testing mocked user flows.

regressions, 14 Chromium/WebKit browser checks, TypeScript checks, and the
production build. Lint reported no errors and existing repository warnings.

### Remaining production validation

No real show has been published or uploaded to either provider as part of these
tests. A real four-hour show must still be checked for provider acceptance,
playable duration, scheduling and saved episode metadata after deployment. The
exact cause of Sam's historical production crash cannot be asserted without its
runtime logs.

The form's existing size/format allowance still exceeds RadioCult's documented
support; this fix does not increase provider limits. Long transfers still have
the existing function deadlines, and the browser still coordinates the two
destinations. Persistent jobs remain a separate improvement if slow production
transfers hit those deadlines or surviving a closed tab becomes a requirement.

## Optional future background-job design

Keep the browser's direct multipart upload to Blob. Replace the two long browser
requests with a short, authenticated request that creates a persistent upload
job and returns its identifier. Bind the source Blob and episode to that job.
Record the original filename, byte size, title, hosts, description, artwork,
broadcast time, and existing provider results.

Use a background worker to stream the file to each provider with backpressure.
Memory must remain bounded as file size grows. Preserve RadioCult's ID3 rewrite
using a bounded prefix read and streaming skip of the old tag; do not read the
old tag or entire master into memory. Preserve Mixcloud's scheduling, host tags,
description limits, and artwork behavior. Avoid HTTP libraries' redirect replay
buffers; reopen the immutable source only for a safe, explicit retry.

Persist each destination's state and returned identifier immediately. Include
`queued`, `transferring`, `succeeded`, `failed`, and `needs-verification` states.
Lease jobs atomically so concurrent workers cannot publish the same job. If a
connection dies after sending the file, the outcome may be unknown: reconcile
with the provider or ask for an operator check instead of automatically creating
a duplicate. An episode-save failure must retry persistence, not the upload.

Let the browser poll the job. Refreshing or closing the page must not lose its
progress. Retry only a confirmed failed destination and retain the source until
both destinations and episode persistence are confirmed. Apply a documented
retention policy to abandoned jobs, with deliberate cleanup rather than deleting
potentially recoverable audio on failure.

Check supported formats and each destination's size limit before uploading the
source. Specify decimal bytes versus MiB explicitly and account for the small
ID3 size change. Do not silently transcode or reject a Mixcloud-only workflow
using RadioCult's restrictions.

## Hosting decision

No existing durable job queue or worker infrastructure was found in this repo.
A dedicated Node worker plus transactional job storage is the preferred design
for transfers that may outlast an HTTP function. Hosting and pricing need to be
agreed before provisioning; nothing has been provisioned.

If the constraint is Vercel-only, evaluate a durable workflow plus streaming
steps. A workflow does not remove the execution limit of an individual transfer
step. Prove the slowest supported transfer fits that limit before choosing this
option. A larger function memory allocation alone is not the proposed fix.

RadioCult also exposes an endpoint to forward an existing track to Mixcloud.
Do not substitute it without verifying scheduled publication, returned Mixcloud
URL, connected-account behavior, artwork, and recovery semantics against the
current workflow; the documented upload fields do not include a publish date.

## Required verification before rollout

- Preserve existing small-file, metadata, scheduling, archive, and partial-success tests.
- Run real Node HTTP transfers with generated 557.2 MiB files and files near the
  supported boundary; measure peak RSS under a slow receiver and concurrent jobs.
  Assert transmitted audio hashes and multipart lengths, including ID3 replacement.
- Cover source stalls, destination stalls, broken connections, rejected files,
  HTML/non-JSON errors, and the receiver accepting a file before its response is lost.
- Kill and restart the worker; refresh and close the browser; duplicate the
  submission; verify recovery and that successful destinations are not repeated.
- Test lease expiry, storage outages, archive failure, and cleanup failure.
- Run a controlled real four-hour audio transfer through both providers and
  verify duration, metadata, schedule, playback, and saved episode identifiers.
  Local mocks cannot validate those provider behaviors.

The implemented fix is the streaming/import/error-handling work above. The
background-job design is not implemented or provisioned.
